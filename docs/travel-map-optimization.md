# 游记地图资源优化调查

调查日期：2026-10-14。对象：当前关西机场到京都的游记，9 个地点、6 组不同坐标。

## 结论

建议先解决生成资源进入 Git 的问题，保留已经验收的静态连续移动。这样可以直接消除日常提交中的大量二进制文件，又保留当前的首屏和移动表现。

“点位 WebP + 动态矢量地图”技术上可行，适合作为后续候选。它需要同时解决沿途数据准备、资源裁剪、渐进切换和弱网降级；只把中间 WebP 换回原地图服务的实时 PBF 请求，会重新引入加载等待。现有证据不足以认定混合渲染比当前实现更快，应先做同文、同设备、同网络的比较。

380 张图片和清单均已进入 Git，提交 `4067196` 的地图目录包含 381 个新增文件。浏览器按当前主题、尺寸和阅读位置加载附近图片，37.17 MB 是整套发布资源量，不是首屏下载量。

当前生成器会复用已有且匹配的结果；纯文章文字修改不改变地图键。坐标、样式或缩放配置变化会产生新的地图键；路线绘制也可能影响大量图片。因此，二进制资源持续进入 Git 会累积历史成本。

## 矢量资源实测

使用现有 Native 渲染流程、同一份相机清单和 24% 边缘余量，在临时目录重放全部采样。浅色与深色各覆盖桌面 89 个、手机 101 个不同相机，按资源 URL 去重。未修改现有图片或页面。

| 资源                         | 去重数 | 解压后字节 | 逐资源 gzip 字节估算 |
| ---------------------------- | -----: | ---------: | -------------------: |
| 地图矢量瓦片                 |    235 | 33,443,054 |           20,930,911 |
| 字体 PBF                     |    164 | 32,737,965 |           21,712,528 |
| 样式、TileJSON、精灵图及索引 |      5 |    143,832 |               57,790 |
| 合计                         |    404 | 66,324,851 |           42,701,229 |

数据版本为 `20261011_080001_pt`。这里的 gzip 是本地压缩估算，不是实测公网传输字节，也不是 PMTiles 成品大小。重放覆盖已保存的离散相机采样，不能作为任意窗口尺寸、连续路径全部瓦片均已覆盖的证明。

Native 和浏览器的字体行为不同。MapLibre GL JS 默认通过 `localIdeographFontFamily: 'sans-serif'` 本地生成中日韩字符；当前实时组件未关闭这一选项。因此不能把 Native 的字体请求量直接算到浏览器头上。地图瓦片本身约 20.93 MB 的估算也提示：全量预载原始矢量包并不一定比访问者所用的一套 WebP 更省流量。两类数据的复用方式、视口范围也不同，需要浏览器对照测试。[MapLibre 字体选项](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/#localideographfontfamily)

## 优先方案：生成资源与源码分开管理

保留文章、生成器和小型资源清单进入 Git。WebP 以及将来可能生成的矢量包作为发布产物，由本地缓存、构建缓存或对象存储管理。

建议先采用“构建前恢复或生成，随站点发布”的方式，继续使用 Cloudflare Pages 静态资源缓存。它不要求先引入 Worker。若已有可用的 R2 图片域名，也可以把地图产物上传到该域名下；R2 需要自定义域名和相应缓存规则才能使用 Cloudflare 缓存。[Pages 缓存说明](https://developers.cloudflare.com/pages/configuration/serving-pages/)、[R2 自定义域名缓存](https://developers.cloudflare.com/r2/buckets/public-buckets/)

实现顺序：

1. 建立以地图键、生成器版本和上游数据版本标识的资源缓存；清单记录文件摘要和大小。
2. 在构建读取 Markdown 之前恢复资源；缓存缺失时执行现有原生生成器，并校验所有清单引用。
3. 缺失或校验失败时终止生产发布，避免静态模式下发布没有地图的页面。地图发布构建集中在支持原生依赖的环境中执行。
4. 验证干净检出的构建与部署后，再取消 Git 对 WebP 的跟踪并加入忽略规则。仅添加 `.gitignore` 不会停止跟踪已有文件。
5. 按内容摘要增量发布，保留旧部署仍引用的资源，另行清理未引用版本。

当前 `readStaticTravelMap` 要求清单引用的图片在本地存在，所以即使配置 `staticBaseUrl`，也需要调整或满足构建前的资源校验。直接忽略图片、继续使用当前 CI 构建，会丢失地图。普通构建缓存也可能失效，必须有明确的恢复或重新生成路径。

取消跟踪解决后续提交负担，不会自动删除已经进入 Git 历史的图片；本方案不需要重写历史。

## 混合渲染候选设计

首屏先显示总览或当前点位的 WebP；后台准备矢量地图。矢量层与图片层使用同一套阅读进度和相机参数，当前视口的数据和绘制就绪后再渐变切换。加载失败、节省流量或设备无法使用 WebGL 时，保留点位图片作为基本体验。降级时会牺牲点到点的连续移动，应在验收中明确这一取舍。

只保留现有端点图片即可从 380 张降至 28 张，图片资源约减少 90.6%；这是 WebP 部分的变化，动态地图的数据和客户端渲染成本需要另外计算。

矢量数据应在发布前准备：根据相机实际扫过的区域和缩放层级收集瓦片，包含总览、点到点拉远轨迹和视口边缘。不能只缓存地点所在的瓦片，也不宜把整段路线的包围盒在所有高缩放级别全部下载。明暗主题共用几何数据，删除不使用的源图层与属性，字体采用浏览器本地生成或经过验证的子集。

可把瓦片组织成 PMTiles，减少产物管理和上传时的文件数。它是瓦片归档格式，浏览器仍会发起多个 HTTP Range 请求，仍需 MapLibre 解码、布局和绘制；它不等于一次请求完成整张地图。[PMTiles 原理](https://docs.protomaps.com/pmtiles/)、[MapLibre 接入](https://docs.protomaps.com/pmtiles/maplibre)

Cloudflare Pages 官方目前说明 Range 请求返回 200，而非标准 206，因此不能直接假定 Pages 上的 PMTiles 可以高效按需读取。候选部署应使用实测支持 206 的 R2 自定义域名，或采用官方的 R2 + Worker Z/X/Y 瓦片接口；后者仍有多次瓦片请求，应验证缓存命中和冷启动表现。[Pages Range 行为](https://developers.cloudflare.com/pages/configuration/serving-pages/)、[PMTiles Cloudflare 部署](https://docs.protomaps.com/deploy/cloudflare)

显示切换需要同时检查样式、当前视口瓦片和实际绘制状态；一次初始 `load` 不能代表之后每个位置都就绪。快速跳转或反向滚动时，应保留最后完整画面或对应点位图，避免展示缺块的矢量层。HTTP 字节预取也不等于 GPU 已完成绘制。[当前视口瓦片检查 API](https://maplibre.org/maplibre-gl-js/docs/API/classes/Map/#aretilesloaded)

## 候选方案比较

| 方案                           | 提交负担                 | 首屏与移动                           | 判断                           |
| ------------------------------ | ------------------------ | ------------------------------------ | ------------------------------ |
| 当前 WebP 移出 Git，构建恢复   | 直接消除二进制提交       | 保留当前已验收表现                   | 优先实施                       |
| 点位 WebP + 原地图服务实时 PBF | 图片减少，PBF 不进 Git   | 首屏可快，沿途仍受上游请求影响       | 不足以保证加速                 |
| 点位 WebP + 裁剪矢量包 + CDN   | 少量图片和归档产物       | 可连续移动，需要测客户端开销         | 后续对照实验                   |
| 将现有 WebP 打成 ZIP 或大图集  | 文件数减少               | 需要解包或大图加载，妨碍当前按需加载 | 不作为首选                     |
| Git LFS                        | 改为管理指针和外部二进制 | 浏览器行为不变                       | 可管理大文件，不能独立加速页面 |

## 混合方案替换前的验收条件

- 用当前文章比较首张完整地图出现时间、总传输量、连续滚动流畅度与内存；分别测桌面、手机和明暗主题。
- 验证冷缓存、热缓存、弱网、快速跨段跳转、反向滚动、主题切换和矢量资源失败。
- 验证字体和路线风格差异，确认切换前后地点位置一致。
- 验证动态层仅在完整画面就绪后显示；WebGL 不可用时仍能看点位地图。
- 如采用 PMTiles，实测 206、Content-Range、CORS 和边缘缓存；如采用 Worker，实测 Z/X/Y 接口的冷、热缓存。
- 干净检出后可恢复产物并完整构建；日常修改文章不会产生数百个二进制提交项。

本次完成资源盘点、原生资源重放和官方文档核对。页面仍使用当前静态连续移动实现；尚未制作混合渲染原型，也未部署或测量线上 Cloudflare 缓存。

## 实施进展（2026-10-15）

第一阶段已实施：生成图片取消 Git 跟踪，小型清单保留；开发与构建前自动检查本地资源、恢复缓存或原生生成。CI 接入资源缓存和产物传递，静态模式缺图时生产构建失败。缓存使用现有地图键区分坐标、配置与渲染版本，以每张图片的内容摘要验证产物；上游底图的更新通过显式 `--force` 触发，缓存不会自动追踪上游变化。

当前文章恢复后的图片字节和地图运行方式保持一致。完整验收与远端运行限制见[验收记录](./travel-map-acceptance.md)。混合渲染保留为后续对照实验。
